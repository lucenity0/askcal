Askcal

Your inbox, ranked by regret.

Every mail tool you have ever used sorts by when things arrived. Nothing arrives in the order of what it costs you to ignore it. Askcal reads your mail, scores each message by what missing it would actually cost, and turns the ones that matter into a day — already arranged around your calendar.

The premise

Recency is not consequence.

A newsletter that landed a minute ago sits above a fee notice from Tuesday. Both look identical in a list, so you read both, and the one with a deadline is the one you scroll past. That is not a discipline problem. It is a sorting problem, and no amount of inbox-zero fixes a list that was never ordered by what matters.

Askcal asks a different question of every message: what does ignoring this cost me? A missed assessment costs an opportunity. An unpaid fee costs money. A newsletter costs nothing, however recently it arrived and however urgently it is written.

How it decides

The model extracts signals. Arithmetic does the scoring.

A language model is good at reading an email and bad at being consistent about a number. So it never produces the score. It extracts what it can actually judge — the stakes, the sender, whether there is a concrete task, when it is due — and a deterministic formula turns those into 0–100.

score = consequence (35 opportunity · 35 grade · 30 money · 12 social · 4 none)
      + deadline proximity (40 within a day, decaying to 10 within a week)
      + sender  + action required
      × track weight  × confidence  → clamped 0–100

Every score is reproducible from the signals stored beside it. When a task ranks oddly you can read why, rather than asking a model to explain itself after the fact.

Tracks

A PR review is work. It was filed under Design.

Askcal shipped with five categories — career, uni, design, finance, feed — baked into the database, the prompt and the app. They described a guess at someone's life rather than anyone's actual life. Asked to pick one of five for a code review, the model picked the closest, and the closest was wrong.

Before

Five names in an enum. The prompt described them in fixed prose. Changing one meant a migration and a rebuild.

After

Tracks are rows you name. You write what belongs in each, and that sentence is what the classifier reads.

Which is the whole fix: a track called “work” tells a model nothing. “Anything from my team or about a PR, even when I'm not working” moves the review out of Design in one edit, with no deploy.

Mailboxes

College mail and personal mail. One day.

Not an account switcher — there is nothing to switch. Every mailbox you connect pours into the same list, is scored on the same scale, and becomes work on the same day.

Each mailbox carries the tracks its mail is usually about, and that reaches the classifier as a leaning rather than a rule. It has to be: a bill arriving at a college address is still about money, and a mailbox that overrode the content would be confidently wrong every time, with nothing on screen explaining why.

The pipeline

Mail lands first. Judgement follows.

  1. Ingest. Every connected mailbox is pulled on a schedule. One dead mailbox costs you that inbox, not the pass.

  2. Store. Raw mail is written immediately, unscored. Classification never blocks ingestion, so a slow model never costs you an inbox.

  3. Classify. One call per batch, structured output validated against the same model the prompt is generated from — so prompt and parser cannot drift.

  4. Score. The deterministic formula, weighted by how much that track matters to you.

  5. Gate. A confidence floor and a stakes floor. A model's guess should not become your Tuesday.

  6. Plan. What survives is placed around your real calendar — deadlines first, then consequence, never into an hour that has already passed.

What it cost

The decisions worth defending.

Encryption is a column type, not a call site.

A Google refresh token is a long-lived key to an entire mailbox and calendar. Encrypting it wherever it is written means the one place that forgets writes plaintext into a column everything else assumes is safe. It is a SQLAlchemy type instead, so forgetting is not available. Stored values carry a version prefix, which is what let the key be switched on without taking a single mailbox offline.

The classifier is measured, not eyeballed.

Every prompt change used to be validated by waiting for real mail and seeing whether it looked right — which finds a regression days later, on the one message that mattered. A golden set of twelve cases, each carrying the rule it exists to pin, now answers the same questions every time. Two of them found errors in the fixture before they found any in the prompt.

The same bug, four times, in four disguises.

A classifier silently unconfigured. An inactive track blocking every task under it. Carried work losing its day. Auto-task rules that only ever ran once, at classification. All four are one shape: state that decides whether work reaches you, applied invisibly, with no way to see or change it. Everything added since has to answer for all three.

Migrations that can be undone.

Three schema changes each added the new shape beside the old one and backfilled, so every step deployed alone and could roll back. The columns came out much later, in a migration whose own docstring says it restores the shape and not the data.
